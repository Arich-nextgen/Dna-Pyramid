# CODEX — PYRAMID DNA: реальная инженерная доработка, не админ-панель

Ты работаешь в моём **существующем** репозитории PYRAMID DNA. Это система анализа RU/KZ финансовых предложений, выделения условий и сопоставления **структуры финансовых механизмов**. Завтра продукт должен работать стабильнее и давать **проверяемые, воспроизводимые доказательства**, а не больше экранов.

**Первая команда:** изучи фактическую структуру репозитория, `pyramid_dna_engine.py`, FastAPI, frontend, тесты и реальные scripts из package.json. Не выдумывай папки или технологии. В корень проекта я добавлю распакованный `pyramid_dna_external_challenge/`; сохрани пакет без переписывания его золотых меток.

## Нерушимые ограничения

1. **НЕ СТРОЙ АДМИНКУ.** Ни новой dashboard-панели, ни CRM, ни ролей, ни таблиц пользователей, ни постоянной левой боковой панели, ни «центра управления», ни выдуманных интеграций. Сохрани существующие страницы «Проверка», «Сравнение», «Материалы», «Методика» и страницу реального качества (даже если она скрыта из верхнего меню). Новая визуализация — только компактно внутри существующего процесса.
2. Не переписывай сайт с нуля, не ломай горизонтальную навигацию, тёплую нейтральную палитру, сохранённые дела, TXT-импорт, мобильный layout и API. Не добавляй градиенты, glassmorphism, неон, декоративные графики. Не переписывай существующий Python matcher целиком без доказанной необходимости.
3. Все выводы только из **реальных вычислений**. Запрещены фиктивные проценты, mock JSON как production, статичные “96.6%” и “100%”, заранее назначенные оценки примерам, числа вшитые в UI. Не скрывай ошибки и не называй предварительный риск юридическим решением.
4. Не трогай 720 исходных синтетических записей, splits и `mechanism_id`; не добавляй в train/validation/test официальные кейсы. Не используй внешние кейсы для подбора порога и гиперпараметров. Никогда не запускай скрейпинг закрытых чатов и не заявляй об интеграции с АФМ/полицией.
5. **Пакет данных имеет два уровня:** 15 уже измеренных официальных пересказов — *development/diagnostic*, а ещё 5 — *reserved holdout*. Не открывай `public_final_holdout_gold_DO_NOT_READ_BEFORE_FREEZE.jsonl`, не анализируй тексты из `public_final_holdout_inputs.jsonl` и не вычисляй по ним предсказания до freeze кода и порога. Нельзя называть повторный прогон первых 15 «unseen». Разметка holdout отделена процедурно, а не криптографически.
6. У тебя есть разрешение **самостоятельно**: редактировать код/типы/API, добавлять обоснованные dev-dependencies, писать тесты и Python-скрипты, запускать их, делать минимальные миграции с сохранением данных, фиксировать версии экспериментов, исправлять ошибки и рефакторить узкие места. **Нет разрешения** стирать пользовательские дела/IndexedDB/localStorage/SQLite, удалять работающие функции, публиковать данные, менять область проекта или менять критерии эксперимента после test.

## P0 — сначала сделать ЭТО, по порядку

### 0. Зафиксируй отправную точку

Проверь git status и текущие тесты. Не стирай незакоммиченные изменения. Сохрани commit SHA / engine SHA-256, исходные test-метрики, seed, версию Python. Проверь реальную архитектуру frontend: браузерный Python/Pyodide, Worker, API или смешанный вариант — **не предполагай**.

### 1. Исправь настоящую слабость: извлечение финансовых условий

В приложенном `artifacts/public_challenge_results.json` исходный движок извлёк **28/45** размеченных признаков, в том числе `needs_deposit` только **2/15**, `period_days` **2/6**, при `has_return_claim` **15/15**. Это честный диагностический baseline, не целевые числа для подгонки.

Исследуй `analyze()`, `money_mentions()`, `get_money_roles()`, `extract_period()` и словари RU/KZ. Исправь общую логику, которая делает наличие взноса зависимым от обнаружения суммы исключительно в ₸. Разведи три понятия: **есть требование вложить средства**, **денежная сумма упомянута** и **известна конкретная валюта/роль суммы**. Поддержи RU/KZ формы вложений, USD/EUR/USDT/KZT, диапазоны, проценты доходности, ежедневные/ежемесячные/через N дней; различай обещанную прибыль, выплачиваемую сумму, проценты вознаграждения реферала, стоимость пакета и общую сумму ущерба. Не конвертируй валюты по выдуманному курсу. Не принимай сумму ущерба из новостной статьи за первоначальный взнос.

Сохрани старые `fingerprint`-ключи ради API-совместимости; новые поля добавляй типизированно и опционально, с `currency`, `min/max`, `unit`, `role`, `source_span`, `confidence` только там, где уверенность обоснована. Не заполняй `null` догадками. Проверяй отрицания: «доход не гарантирован», «без взноса», обычная покупка, критический/предупреждающий текст. Отдельно учитывай, что пересказ официальной публикации — **сообщение о схеме**, а не реклама от самой схемы: извлечение финансовых утверждений допустимо, но нельзя автоматически трактовать его как новый исходящий мошеннический пост. Не устанавливай идентичность организатора по similarity.

**Критерий готовности:** новые юнит-тесты для RU, KZ, USD/EUR/USDT, диапазонов, процентов, периода, отрицаний и доброкачественных контекстов; исходные API-тесты проходят. Ошибки исправляй на самостоятельно составленных **новых** unit/dev fixture, а первые 15 используй лишь для прозрачной диагностики после изменений.

### 2. Реальный Benchmark Arena: structural matcher против TF-IDF

Создай/исправь `scripts/run_benchmarks.py`, `requirements-dev.txt`, `artifacts/benchmark_results.json` (реально сгенерирован). Сравнивай **matching механизмов**, не accuracy классификатора риска. Используй **одинаковые пары** для DNA и TF-IDF; запрети пересечение `mechanism_id` между train/validation/test; TF-IDF vocabulary fit **только на train**, порог TF-IDF выбрать **только на validation**, и один раз измерить test. Для DNA используй существующий фиксированный порог или корректно подбери его на validation и заморозь перед test. Один фиксированный seed, сохранённые количество positive/negative pairs, precision, recall, FPR, матрица ошибок, thresholds, версии/хэши. Добавь тесты на leakage и корректность pair construction. При необходимости добавь word и char n-gram baseline, но не откладывай результат ради усложнения.

**Важно:** числа из исследовательского Word-документа — гипотеза/предыдущий расчёт, а не разрешение хардкодить метрики. Если твой воспроизводимый результат отличается — показывай измеренный результат и причину.

### 3. Feature-level similarity — раскрыть математическую сущность DNA

Минимально расширь `compare()` и API-ответ `feature_comparison`: имя финансового признака, A, B, `exact_match|partial_match|conflict|missing_left|missing_right|unknown`, вес, сырое начисление, доля после нормировки, текстовое объяснение. Сумма вкладов должна **математически соответствовать** итоговому similarity (с тестом на допустимую погрешность), `missing` не должно означать совпадение, отсутствие обоих признаков нельзя награждать очками. Сохрани `shared_features` и старые ключи для совместимости.

В существующем экране «Сравнение» покажи **ОДНУ** аккуратную таблицу «Финансовые условия»: «Условие / Материал A / Материал B / Совпадение / Вклад». Суммы, валюта, срок, обещанный доход, приглашение/рефералы должны читаться сразу. Обозначай «недостаточно данных». Сохрани независимые TXT A/B, ручное редактирование, существующие действия и видимый главный CTA. Не создавай страницу «управления отпечатками».

### 4. Внешняя проверка — не спутать с обучением

В проекте уже лежит `pyramid_dna_external_challenge/`. Проверь JSONL схему и официальные URL. Используй существующий `scripts/eval_public_challenge.py`, не меняя его для искусственного увеличения показателей. Публикуй `artifacts/public_challenge_results.json` с датой, engine SHA, input SHA и метками **diagnostic/development**; ошибки фиксируй по каждому полю и ссылке. После завершения всех изменений, тестов и freeze версии только **один раз** запусти 5 отложенных кейсов с `--gold-file` и сохрани `artifacts/public_final_holdout_results.json`. Если видел gold до freeze — признай holdout недействительным и не называй его слепым.

Небольшой блок «Проверка на открытых кейсах АФМ» добавь **лишь в существующий раздел качества/методики** или ненавязчиво в материалы: покрытие извлечения, проверяемые источники, несколько ошибок. Подпись: «Подготовленные по официальным публикациям пересказы, не исходные сообщения соцсетей». **Не** создавать админку, отдельный портал, очередь модерации и большие KPI-дашборды.

### 5. Стабилизируй запуск и обновление страницы

Диагностируй, почему F5 повторно готовит Python. Измерь cold/warm загрузку, исключи двойную инициализацию runtime и лишние rebuild индексов; cache/worker/prewarm только если полезны в **реальной** архитектуре. Не показывай глобальный гигантский loader и постоянное «Загрузка Python» в header. Страницы и сохранённые дела должны быть доступны без готового движка; локальный статус только при запросе анализа, понятная ошибка/повтор при сбое, без фиктивных ответов. Не уничтожай SQLite, IndexedDB, localStorage, миграции и сохранённые записи.

## P1 — делать ТОЛЬКО когда весь P0 готов и проверен

- `scripts/robustness_suite.py`: RU↔KZ, mixed/translit, пробелы/эмодзи, перестановка фраз, отдельные контрпримеры «не гарантирован», «обычная покупка», «предупреждение». Выводи mechanism invariance и benign suppression, без статичных процентов.
- `scripts/calibrate_threshold.py`: используй **только validation** синтетической базы, фиксируй конфиг в `config/matcher.json` до теста. Нельзя подгонять по официальному challenge/test.

- Три воспроизводимых сценария для анализа, RU↔KZ сравнения и доброкачественного примера. Проверить TXT A/B. Для пользовательского теста подготовь 10-минутный сценарий на 3 человек, но **не утверждай, что тест проведён**, если никто его реально не прошёл.

## Обязательный прогон и Definition of Done

Установи только нужные зависимости. Выполни доступные Python-тесты, `python -m pytest -q`, dataset validation, benchmark, external diagnostic, test сравнения API, frontend typecheck/lint/build из **существующих** scripts, smoke endpoints `/healthz`, `/api/v1/analyze`, `/api/v1/compare`, реальный запуск приложения. Если браузер недоступен, честно сообщи, а не имитируй его проверку.

**Порядок работы:** сначала короткий список фактических файлов/проблем; затем сразу редактируй и проверяй. Не присылай одну «архитектурную концепцию» вместо реализации. Если не успеваешь весь объём, завершай работающий P0 вертикальный срез: **исправление extraction + замеры + feature comparison + стабильный F5**; P1 оставь с точным статусом, не создавай пустые заглушки.

**Финальный ответ Codex — только факты:** изменённые файлы; команды и PASS/FAIL; измеренные числа с происхождением; SHA/commit; что показал резервный holdout, если был корректно проведён; что не сделано и почему; ничего о жюри, презентациях или том, как эффектно выглядеть.
